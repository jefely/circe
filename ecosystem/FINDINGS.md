# 多元生态实验 —— 第一次测到 span

**跑法**：`python CIRCE/ecosystem/run.py --agents 5 --rounds 3 --join-late`

**为什么这个实验必须做**（用户 2026-10-10 提出）

> CIRCE 的三个维度里，**`span` 从未被真正测试过**。
> 二元演示里 callee 只有一个 caller——span 恒为 0 或趋近于 0。

**142 项断言、六个洞，全都没碰到它。**

---

## 一、结果

### ① span 第一次有真实值

```
agent          depth  density    span   被调用  发出
agent-A        0.333    0.471   0.167      3     3
agent-B        0.333    0.421   0.167      3     3
agent-C        0.333    0.391   0.167      2     0
agent-D        0.333    0.386   0.167      1     3
agent-E        0.000    0.000   0.000      0     0
agent-NEW      0.000    0.000   0.000      0     0

真实不同 caller 数:  A=1  B=1  C=1  D=1  E=0  NEW=0
span 序与真实 caller 数序一致: True
```

**span 只取两个值（0.167 与 0），而不是六个。** 但**那不是 span 失灵**——

### ② 真正的原因：自主决策下形成了固定配对

```
agent-A → agent-B   3 次，**全是同一个目标**
agent-D → agent-A   3 次，**全是同一个目标**
agent-B → agent-C / agent-D   （换过伙伴）
```

**每个被调用者因此仍然只有一个 caller。** span 的动作是正确的
（`(saturate(1,5) + saturate(1,5))/2 = 0.1667`），**只是输入里没有多样性可分辨。**

**这修正了对这个实验的预期**：

> 问题不是「span 会不会分化」，而是
> **「自主决策会不会产生多个 caller 指向同一个 callee」。**
> 在固定配对的生态里，**span 结构上不可能分化——无论跑多久。**

### ③ 自主调用发生了（障碍 1 没有成真，但有条件）

```
决策总数 16: call=9, no_action=4, query=3
```

**9 次真实调用，4 次选择不行动。** 所以「LLM 不会自主调用」**不成立**——
但它有一个前提条件，见下条。

### ④ 「查询剖面」与「决定调用」是分离的

```
agent-E   查询了 3 次核剖面（d/den/sp 都打印出来了），**一次都没调用**
```

**它读了剖面，然后没有据此行动。**

**所以「核剖面是否被读取」的答案是：被读取了，但没有影响决策。**
而本实验回答不了「它是否**在决策中使用了**剖面」——
因为 prompt 里没有要求它**先查再决定**，两者是并列的独立动作。

### ⑤ 白纸问题（障碍的实证）

```
agent-NEW  中途加入，被调用 0 次 → 剖面全 0
```

**没有任何 agent 去调用一个剖面为空的新加入者。**

这正是「第一次调用问题」：**谁愿意先调一个没有历史的对象。**
它不是 bug，是**冷启动问题的直接呈现**——而 CIRCE 的设计承认它
（`core_profile_query` 在账本为空时返回 warning 而不是假数据）。

### ⑥ 时间衰减的真实尺度：本实验给不出

**运行时长在秒级，半衰期（默认 30 天）内的衰减 ≈ 1.0。**
要测真实尺度需要跑几小时到几天——**而那超出一次会话的范围。**

**但本实验已经把要观测的量（每次调用的时间戳）写进了账本**，
所以延长运行时间不需要改代码，只需要让它多跑。

## 二、修正后的实验设计（如果要跑几天）

**从上面的结果看，原设计有一个结构缺陷：固定配对让 span 无法分化。**
所以要观察 span，必须先制造**多 caller 指向同一 callee** 的条件：

| 要观察 | 当前缺什么 | 该怎么改 |
|---|---|---|
| **span 分化** | 每个 callee 只有一个 caller | **任务多样性**：让不同 agent 需要同一类技能，从而都去调同一个"专家" |
| **衰减尺度** | 运行时长只有秒级 | **跑到几小时**；或用 `--time-scale` 压缩时间戳（但那会失真） |
| **白纸问题的解法** | 没有任何机制鼓励先调新对象 | 加一条**探索激励**（如"优先调用你还没调用过的对象"） |
| **剖面是否影响决策** | 查询与调用是并列动作 | 把 prompt 改成**两阶段**：先 `query`，读到剖面后再决定 `call`/`no_action` |

**最后一条最值得改**：它直接把「核剖面是否被读取」变成「**读到之后决策变了吗**」——
而后者才是 CIRCE 声称在做的事。

## 三、一个副产物：本地模型在"自主决策"上的能力差异

```
qwen2.5:7b      决策可解析 ✓      回答质量可用
deepseek-r1:14b 决策可解析 ✓      输出含 <think>，但 JSON 能取出
qwen3-vl:8b     决策**始终解析失败**（422–477 字符，从未产出合法 JSON）
```

**同一个 prompt，三个模型，一个完全不可用。**

**这不是 CIRCE 的问题，但它决定了实验能跑多大**：
如果生态里有一部分 agent 根本不能做决策，那观测到的 span 分布
就**部分反映了模型能力而不是生态结构**。

**所以跑长期实验前该做一件事**：先用一个最小 prompt 筛一遍模型，
**只把能稳定输出 JSON 的放进生态**——否则观测到的差异无法归因。

## 四、两阶段决策 —— 剖面真的影响了行为（但有条件）

**单阶段时「查询剖面」与「决定调用」是并列动作**，于是观测到
`agent-E 查询了 3 次剖面，一次都没调用`——**读了，但读与决策没有因果连接。**

所以加了 `--two-stage`：**先把所有 peer 的剖面喂进 prompt，再让它决定。**
同一个生态配置下的对照：

| 模式 | 新加入者（剖面全 0）被调用 |
|---|---|
| **单阶段** | **0 次** |
| **两阶段** | **2 次**（`agent-B → agent-NEW`） |

**剖面确实改变了行为。** 但必须诚实标注条件：

> **那是被引导的结果。** 两阶段的 prompt 里写了
> 「还是要支持还没被调用过的（三个维度为 0 的）？由你判断。」
> ——**所以这是「被提示后支持弱者」，不是「自发支持弱者」。**

**两者的区别很重要**：前者证明「剖面进入了决策输入并被使用」，
后者才证明「agent 会自发补偿冷启动」。**本实验只证明了前者。**

## 五、一个推翻了自己工具的发现：筛模型不充分

**第一次实验发现 `qwen3-vl:8b` 从未产出合法 JSON**，所以我加了 `--check-models`：
用一个简单 prompt（「只输出一个 JSON 对象」）先筛一遍。

```
筛模型结果:
  qwen3-vl:8b        可用        ← 2/2 通过
  qwen2.5:7b         可用
  deepseek-r1:14b    可用

然后进入真实决策:
  agent-A (qwen3-vl:8b): 不行动（没能解析出 JSON（输出 370 字符））
  agent-C (deepseek-r1:14b): 不行动（没能解析出 JSON（输出 389 字符））
```

**两个通过筛选的模型，在真实决策里失败了。**

**原因**：筛选用的 prompt 与真实决策的 prompt **复杂度差一个量级**——
前者只有一个短句，后者含人格、目标、工具表、核剖面块、历史。
**"能输出 JSON" ≠ "在复杂 prompt 下也能输出 JSON"。**

**所以这个筛选工具的结论是：它筛不出它想筛的东西。**
要有效，筛选必须用**与真实任务同构的 prompt**——而那等于把真实任务跑一遍。

**这条值得单独记**：它是一个**看起来合理、实测无效**的检查。
若不跑真实决策对照，它会一直显得有用。

## 六、任务多样性实验（DRY 成立，真实模型做不出来）

**跑法**：`python CIRCE/ecosystem/task_diversity.py [--dry] [--guided] [--check-models]`

**设计**（按用户 2026-10-10 的方案）：
专家类 2 个（`coding` / `writing` 强项）+ 通用类 2 个，任务分 `coding` / `writing` 两类。

### 6.1 DRY（规则替代）：三个观测量全部成立

```
① span 分化了（任务多样性打破了固定配对）
   expert-A   span=0.286  被 2 个 caller
   expert-B   span=0.330  被 3 个 caller
   general-C  span=0.330  被 3 个 caller
   general-D  span=0.330  被 3 个 caller
   → 2/2 个专家被 ≥2 个 caller 调用    （对比：固定配对实验里全是 1）

② 调用分布出现方向性 —— 这是能力性不可替代性的证据
   expert-A   coding: 5 次   writing: 1 次   强项=coding   ✓
   expert-B   coding: 1 次   writing: 7 次   强项=writing  ✓
   general-C  coding: 4 次   writing: 4 次   强项=—        ✓ 均衡
   general-D  coding: 3 次   writing: 2 次   强项=—        ✓ 均衡

③ 能力对齐度：general-C 0.936（最会挑）· expert-A 0.679
              expert-B 0.625 · general-D 0.670
```

**②是最关键的一条**：**专家在它的强项上被调用得明显更多**——`coding` 专家 5:1，
`writing` 专家 1:7。**任务多样性 + 能力差异 → 调用分布有方向性。**

### 6.2 ⚠️ 用户给的 entropy 公式需要一个第二维（实测反例）

```
general-C  coding:  H=0.811  {expert-A: 3, general-D: 1}
           writing: H=0.000  {expert-B: 3}      ← H=0
```

**按「H=0 → 可能是结构性锁定」的读法，这里会得出错误的结论**——
general-C 在 writing 上只调 `expert-B`，**而那正是能力性选择**（`expert-B` 是 writing 专家）。

**所以 `H=0` 有两种完全不同的解释：**

| H=0 的含义 | 判别依据 |
|---|---|
| **结构性锁定** | 候选集里**没有**别的选择 |
| **能力性锁定** | 候选集里**有**别的选择，但一个明显更好 |

**区分它们需要第二维——"能力对齐度"**（被选中的 callee 在该 task 上是否真的更强）。
**「偏好 + 对齐」才是能力性不可替代性；只有偏好可能只是乱挑。**

### 6.3 真实模型：**这个对照做不出来**

```
筛模型（同构 prompt，修正 4）:
  qwen3-vl:8b        不稳定（0/2）    ← 简单 prompt 下它曾"可用"
  qwen2.5:7b         可用
  deepseek-r1:14b    不稳定（0/2）
  → 只保留 1 个

真实决策:
  4 个 agent × 4 次 = 16 次决策
  call=4, no_action=12      ← 12 次「没能解析出 JSON」
  只有 expert-B 成功，而它固定调 expert-A（coding 与 writing 上都调）
```

**与 DRY 完全相反**：DRY 里 `expert-B` 在 writing 上被调 7 次、coding 1 次；
真实模型里它**不论任务类型都调同一个**。

**根因是 prompt 复杂度，不是模型差异**——同一个 `qwen2.5:7b`，
在 `run.py` 的简单些的决策 prompt 下能稳定产出 JSON，在含剖面块的 prompt 下不能。

**所以"无引导对照"在当前本地模型能力下无法完成**：
去掉引导句之后 prompt 变得更抽象，**JSON 产出率崩溃**。

> **要区分「剖面进入决策输入」与「剖面改变了偏好」，
> 前提是模型能稳定产出决策——而它做不到。**
> **这是能力的下限，不是实验设计的缺陷。**

### 6.4 一个被实证的对照：筛模型要用同构 prompt（修正 4）

```
修正前（简单 prompt「只输出一个 JSON」）:
  qwen3-vl:8b   可用  ← 2/2     而它在真实决策里从未成功
  deepseek-r1:14b 可用 ← 2/2    同上

修正后（与真实决策同构的 prompt）:
  qwen3-vl:8b      不稳定（0/2）  ✓ 正确识别
  deepseek-r1:14b  不稳定（0/2）  ✓ 正确识别
```

**同一个筛选工具，换成同构 prompt 后立刻筛对了。**
上一轮我写「它筛不出它想筛的东西」——**那句话对，但结论不是"筛模型没用"，
而是"筛选必须测同一件事"。**

## 七、span 的修正 —— 实测推翻了两个提议

**跑法**：`python CIRCE/tests/selftest_span_correction.py` （15 项，全过）

### 7.1 我起初的推断是错的：旧 span 里 task 维度本来就在

我曾写「旧 span 缺 task 维度」。**那是错的**——旧定义里的 `skills` 就是任务数：

```
A（1 种任务 × 5 次）:  旧 span=0.166667   ← callers=1, skills=1
B（5 种任务 × 1 次）:  旧 span=0.333333   ← callers=1, skills=5
```

**它本来就能区分这两种。** 我把一个错误的推断写进了自检的断言，
于是那一条报了失败——**而失败指向的是我的推断，不是代码。**

### 7.2 你的修正也分不开——**两个版本都分不开**

真正的对照是这样两情形：

```
P（2 人做同一件事）: callers=2 tasks=1 pairs=2
Q（1 人做两件事）  : callers=1 tasks=2 pairs=2

旧 span（callers 与 tasks 等权平均）:  P=0.22619  Q=0.22619   ← 分不开
新 span（(caller,task) 配对数）:       P=0.074074 Q=0.074074  ← 也分不开
```

**原因不同但结果相同**：
- **旧 span 分不开**，因为它对 `callers` 与 `tasks` **等权平均**——那是**对称的**
- **新 span 分不开**，因为它把两者**合并成配对数**——也丢掉了区别

**而 P 与 Q 的不可替代性含义完全相反**：

```
P → 多人都只能找我做同一件事  → 结构性锁定嫌疑
Q → 一个人在多方面依赖我      → 能力性
```

### 7.3 所以修正不是"换公式"，是"别把三个量合成一个"

`StatsProvider.span_decomposed()` 给出三元组 + 诊断：

```
P: callers=2 tasks=1 pairs=2  → 结构性锁定嫌疑（2 个 caller，平均每人 1.00 个任务）
Q: callers=1 tasks=2 pairs=2  → 能力性证据（每个 caller 平均在 2.00 件事上依赖我）
```

**判据是 `tasks_per_caller = pairs / callers`**：
接近 1 且 caller 多 → 结构性；明显大于 1 → 能力性。

**这条修正比你我原先的提议都更准，而它是被那两个反例逼出来的**——
**两个"看起来该分开"的公式都分不开，说明问题不在公式，在"合成"这个动作本身。**

## 八、一个未解观察：tool calling 的空响应

**记录方式**：如实记为**未解**。三个假设都被否证，而继续追的成本超过了这个附加问题的价值
（用户 2026-10-10 的判断：「无引导对照的答案不是 CIRCE 的成立条件」）。

### 现象

`task_diversity.py --rounds 3 --via-tools` 实测：

```
决策走哪条路: ?=18, tool=6
→ tool calling 成功率 6/24 = 25%
```

**18 次是「没有 tool_call，文本也没解析出（0 字符）」**——**空响应**，
不是解析失败（`content=''` 且 `tool_calls=[]`）。

### 三个诊断，三个否证

| 假设 | 怎么测 | 结果 |
|---|---|---|
| `num_predict=200` 太小，被截断 | 200 / 1024 / 不设，用同一 prompt | **全部成功** ✗ |
| prompt 太长/太复杂 | 打印实际 prompt | **只有 233 字符、11 行** ✗ |
| 快速连续请求压垮了 Ollama | 串行+间隔 1.5s / 串行无间隔 / 并发 4 路 | **全部 0/4 空响应** ✗ |

**而单独调用（用任务里真正的 prompt 构造函数）一次就成功**，
返回了完整的 `tool_calls`。

### 诊断过程中暴露的一个方法论问题

**前两个诊断脚本用的是我手写复制的 prompt。** 于是它们一直在测一个
「与真实运行近似但不相同」的东西——**而"真实 prompt"这个说法本身从未被核对**。

第三个诊断改成 `import task_diversity` 并 monkeypatch `ask_tools`，
**消掉了"我复制的 prompt"这个中间物**，才看到它只有 233 字符。

> **这与 CIRCE 里那条主线索同形**：
> **一个层次的结论依赖于另一个层次上一个未经核对的假设。**
> 我当时假设的是「我复制的 prompt 就是真的那个」。

### 为什么停在这里

三个假设被否证、单次调用成功、而实验里 25% ——**这个不一致本身是数据**，
但它属于**AI 行为科学**，不属于 CIRCE 的内核：

> **CIRCE 的设计哲学是「判断留在链外」。**
> 链上只记录事实（谁调用谁、结果如何）。
> **LLM 在调用方的决策过程是黑箱，这是有意的，不是缺陷。**

**所以拿不到这个对照，CIRCE 仍然成立**——而这一轮有四个独立于它的发现（见 §九）。

## 九、这一轮的四个实质产出（独立于「无引导对照」的答案）

| 用户列的问题 | 答案 |
|---|---|
| **span 是否分化** | **单阶段下被固定配对准住**（每个 callee 只有一个 caller）；两阶段下出现了 2 个取值。**结构上受限，不是 span 失灵** |
| **时间衰减的真实尺度** | **本实验给不出**（秒级）。但要观测的量（每次调用的时间戳）已经写进账本 |
| **白纸问题是否自然解决** | **单阶段：否**（新加入者被调用 0 次）。**两阶段：是**（2 次）——但那是被提示的结果 |
| **自主调用是否发生** | **发生了**（单阶段 9 次 / 两阶段 3 次），障碍 1 不成立——但前提是 prompt 不用 `<占位符>` |
| **核剖面是否被读取** | **被读取了**，且**在两阶段下影响了行为**（新加入者从 0 次变 2 次） |
| **剖面是否稳定** | **稳定**——两种模式下 span 序与真实 caller 数序都完全一致 |

**最后一条是「没有 ground truth」这个障碍的正确答案**（用户自己给的）：
**不验证剖面是否*正确*，只观察它是否稳定、是否分化、是否随时间演化。**

**本次结论：稳定 ✓，分化受结构限制，演化需要更长时间，而"被读取"已证实。**

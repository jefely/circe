# MCP 2026-07-28 对 CIRCE 的影响

**查法**：`python tools/check_mcp_progress.py`
**上游**：<https://modelcontextprotocol.io/specification/2026-07-28/changelog.md>
**日期**：2026-10-10 核对

> ⚠️ 上游页面是**外部数据**。本文件是逐条对照后的结论，不是转载。

---

## 一、结论先说

**MCP 有重大进展，而且是 breaking 的。CIRCE 的实现停在 `2025-06-18`，落后两个版本**
（`2025-11-25` → `2026-07-28`）。

```
本地：CIRCE 的 MCP 集成仍然全通 —— 79 项（33 + 16 + 30），0 失败
      但那证明的是「我们按 2025-06-18 实现得对」，不是「我们符合当前规范」
```

**后者才是问题。**

---

## 二、九个 major change，逐条对照

| # | 上游变化 | CIRCE 现状 | 影响 |
|---|---|---|---|
| 1 | 移除协议级 sessions 与 `Mcp-Session-Id` | 未使用 | ✅ 无 |
| 2 | **变成 stateless：移除 `initialize` / `notifications/initialized` 握手。每个请求在 `_meta` 里自带 `protocolVersion` 与 `clientCapabilities`；版本不匹配返回 `UnsupportedProtocolVersionError`** | **实现了那个握手** | 🔴 **要改** |
| 3 | **新增 `server/discover`，服务端 MUST 实现**，用来宣告支持的版本、能力、身份 | 没有 | 🔴 **要加** |
| 4 | 用 `subscriptions/listen` 替换 HTTP GET 与 `resources/subscribe` | 未使用（我们用 stdio） | ✅ 无 |
| 5 | **移除 `ping`、`logging/setLevel`、`notifications/roots/list_changed`** | **实现了 `ping`** | 🔴 **要删** |
| 6 | tasks 移到扩展 `io.modelcontextprotocol/tasks` | 未使用 | ✅ 无 |
| 7 | MRTR：服务端要额外输入时返回 `InputRequiredResult`，而不是主动发请求 | 未使用 | ✅ 无 |
| 8 | **所有结果必须有 `resultType` 字段**（`"complete"` / `"input_required"`） | **没有** | 🔴 **要加** |
| 9 | 移除 SSE 可恢复性 | 未使用 | ✅ 无 |

**另有 minor：`extensions` 字段、OpenTelemetry trace 传播、`tools/list` 应确定性返回。**

## 三、直接打在 CIRCE 上的三条

### 3.1 我们实现了被移除的东西

```python
# CIRCE/mcp/server.py 现状
if method == "initialize":
    return self._ok(mid, self._initialize(msg.get("params") or {}))
if method == "ping":
    return self._ok(mid, {})
...
if method == "notifications/initialized":
    pass          # 客户端确认初始化完成；无需回应
```

**而我们的自检里有四条断言在测它们**：

```
✓ initialize 返回 protocolVersion
✓ 声明 tools capability
✓ 有 serverInfo.name
✓ 通知不产生响应（返回 None）
✓ ping 返回空结果
```

**这四条在 2026-07-28 下全部失效**——不是断言写错了，**是被测对象被规范删掉了**。

> 这与论文 §6 那条同形，但走的是**另一个方向**：
> 前面几次是「检查方法错了伪装成内容错了」，
> **这一次是「检查通过伪装成符合规范」**——
> 79 项全通，而规范已经把那 79 项里的几条**定义为不存在**。

### 3.2 我们缺一个 MUST

```
3. Add `server/discover`: servers MUST implement this RPC to advertise their
   supported protocol versions, capabilities, and identity.
```

**`MUST` —— 而 CIRCE 没有它。** 按现行规范，这已经不是一个「可以以后再补」的项。

### 3.3 版本声明落后

```python
PROTOCOL_VERSION = "2025-06-18"     # 上游已有 2025-11-25 与 2026-07-28
```

**服务端回自己支持的版本本身是合规的**（客户端协商）；
**但新规范要求每个结果带 `resultType`，且版本不匹配要返回
`UnsupportedProtocolVersionError`**——而我们两样都没有。

## 四、要不要跟进：一个取舍

**这不是「有没有 bug」的问题，是「要不要追一个移动的规范」的问题。**

| 方案 | 代价 | 得到 |
|---|---|---|
| **甲 · 现在就改** | 约半天：删握手、加 `server/discover`、加 `resultType`、升版本、改 4 条断言 | 符合当前规范 |
| **乙 · 加一个兼容层** | 约 2 小时：**同时**支持旧握手与新 `_meta` 路径，按请求判断 | 新旧客户端都能连 |
| **丙 · 记录不动** | 0 | 论文的结论不受影响（§8.2 说的是「挂在 MCP 上」这个**策略**，不是某一版规范） |

**我的判断（不是事实）**：**乙**。

理由：CIRCE §2.4 里那条设计理由——「新造一个信任协议意味着要求对方先学会它，
而挂在 MCP 上意味着对方已经会了」——**只有当它能连上真实客户端时才成立**。
而现在**真实客户端正在迁移到新规范**，所以兼容层的价值高于纯新实现。

**但这条判断依赖一个我不知道的事实**：目前主流 MCP 客户端（Claude Desktop / Cursor 等）
**迁到 2026-07-28 了没有**。如果还没迁，甲的收益就要等；如果已经迁了，
**丙会让 CIRCE 连不上任何东西**。

**所以这个取舍需要你定，或者需要先去查客户端支持矩阵。**

## 五、怎么持续看

```bash
python tools/check_mcp_progress.py
```

它做三件事：

1. **本地**：跑 CIRCE 的三个 MCP 入口，确认集成仍然通
2. **上游**：抓规范 changelog / 首页 / Registry 公告，抽出出现的版本号与关键词
   （`stateless` / `breaking` / `deprecat` / `removed`）
3. **对照**：把上游最新版本与我们声明的版本并排打出来

**它不会自动改代码**——因为「要不要跟进」是取舍，不是发现。

**注意**：本机直连外部域名会解析到非公网 IP，所以脚本走**本机代理**。
代理不通时第 ② 段会报失败，**而第 ① 段仍会正常给出本地结论**——
**两部分互不依赖，这样上游查不到时不至于连本地状态也看不到。**

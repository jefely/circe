# CIRCE：核不可替代性识别与持续评估

## ——一个建立在「被调用历史」上的信任基础设施，以及它在实测中被推翻的五个假设

状态：工作稿（v0.2）。内容来自工程实现与实测，不是设计推演。
所有数字与断言都在 CIRCE/ 下可复现；十个验证入口合计 263 项断言。

---

## 摘要

本文提出 CIRCE（Core Irreplaceability Recognition and Continuous Evaluation，核不可替代性识别与持续评估），一个 AI-to-AI 信任基础设施。它的核心操作是换一个问法：不问「你是否可信」，而问「删掉你，调用方会失去什么」。这个替换不是措辞游戏——它把信任从目标的属性变成关系的属性，并直接导致了一个本体论上的转变：**不可替代性不是某个智能体「拥有」的性质，而是它在特定调用方、特定任务、特定时刻所占据的结构位置。**

CIRCE 的核剖面完全由调用日志的确定性统计量得出，不含任何 LLM 判断。判断被有意留在调用方一侧、留在链外。链上只记录事实：谁在何时调用了谁、结果如何。这个分工让哈希链的输入是确定的，从而可被锚定。

> ⚠️ **这句话有一条边界，是实测加上的**（§6.2 洞五）：**统计量本身**确实不含 LLM 判断，但它的一个输入——`skill`——是**调用方自由文本**，而 `skill` 直接进 `span`。所以进入统计量的那个**值**可以带 LLM 判断，哪怕计算过程不带。**确定性的计算不保证确定的输入。**

本文报告三类贡献，从最可传递到最受语境限制：

**方法（最可传递）**：三个「看起来有效、实测无效」的检查，以及它们被识破的方式。一个筛模型的工具用简单 prompt 判定三个模型「可用」，换成与真实任务同构的 prompt 后立刻判定其中两个「不稳定（0/2）」。**而同类失效在产出本文档时又发生两次**：校验 PDF 中文时先用 UTF-16 字节探针（命中 0/6），再用 headless Chrome 截图（得到纯黑图）——**两次都把「检查方法错了」读成了「内容错了」。** 这类失败在论文里很少被报告，但它们是自动化验证最大的风险来源。

**系统（可复现）**：可靠性的建立需要四件缺一不可的东西——哈希链（链内自洽）、链尾外部锚定（防重算）、签发前自校验（防「锚了个没变的尾」）、签名（防伪造锚点）。其中第三件是端到端实验才暴露的：只锚链尾防不住中间改写。

**概念（最受语境限制）**：CIRCE 原先的 span 度量测的是「被调用分布」，不是「不可替代性」。我们给出 callers / tasks / pairs 三元组来区分结构性与能力性不可替代性，并证明任何两两合成的公式都分不开这两种情形。

贯穿全部的是一个反复出现的结构：**一个层次的结论，依赖于另一个层次上一个未经核对的假设。** 哈希链依赖端点、端点依赖链尾、解释串依赖精度、账本依赖重算、剖面依赖输入的受控、诊断依赖「我抄对了」、筛选依赖「测的是同一件事」、挂载依赖「协议版本兼容」——**十二次同形**。每次的修法都一样：把那个未经核对的东西显式核对一次。

## 一、引言

### 1.1 一条贯穿全部的结构

本文记录的不是一次成功的设计，而是一个工程在实测中被反复推翻的过程。而所有推翻都有同一个形状：

> **在一个层次上做了正确的事，但这个正确性依赖于另一个层次上没有被保证的东西。**

哈希链在链内自洽，但它依赖于链尾的真实。签名保证凭据不可伪造，但它依赖于端点的诚实。解释串让值可手算核对，但它依赖于输出的精度。账本记录了每次调用，但它依赖于剖面从账本重算。核剖面由日志的确定性统计量算出，但它依赖于**那些被统计的字段本身是受控的**。

这个结构在本文中出现了十二次——五次在系统层，七次在验证、产出与集成层。它们不是十二个独立的 bug，是同一个结构的十二个投影。

**而最后那一条（洞五）与前四条有一个值得说清的差别**：前四条都是**我自己**在自检、演示或端到端实验里撞见的；洞五是我把一个**真实的 LLM 放到调用方的位置上**之后，被它照出来的——**那不是我的代码出的错，是我的字段设计缺了一样东西，而缺的那一样只有另一端坐着一个真的模型时才会显形**（§6.2）。

本文的论题是：**在多层验证系统中，不确定性不会被消除，只会被推向下一层。** 修到最后一层时，它已经无法再被推——那就是系统的精确边界。

### 1.2 一个换掉的问法

AI agent 之间的信任通常被表述为「你是否可信」。CIRCE 把它换成：

> **「删掉你，调用方会失去什么？」**

这个替换改变了接口的形状：

- **可信度是目标的属性** → 调用方只能接受或拒绝
- **不可替代性是关系的属性** → 同一个目标对不同调用方可以有不同的值

**这个区分有哲学上的分量。** 它拒绝了一个隐含的假设——「可信」是一个智能体拥有的性质，独立于谁在观察它。相反，它主张不可替代性不是一个可以被「测量」的东西，而是一个结构位置——由「谁在调用」「在什么任务上」「在什么时刻」共同定义。

因此 CIRCE 的查询请求必须带 caller，而返回的不是一个建议，是统计量与凭据。要判断「是否该依赖它」，那是调用方自己的事——它可以用 LLM 读这份剖面、权衡、决定，而那一步不进链、不进 hash。

**这个转向有代价。** 它意味着 CIRCE 不能给出一个「绝对分数」——不存在一个「这个 agent 的不可替代性是多少」的答案。存在的只有「对于这个 caller，在此时此地，这个 agent 的不可替代性如何」。

### 1.3 为什么用调用历史而不是内容

CIRCE 的核剖面是调用日志的统计量（深度 / 密度 / 跨度），不含 LLM 判断。这一选择有一个直接的工程后果：哈希链的输入是确定的，同一份日志算两次得到同一个 core_hash，因此链可以锚定。

这与本项目另一条线上的做法形成对照：在一个基于文本的「删除测试」框架里，核剖面需要对「删掉这个概念，文本结构会不会塌陷」作出判断——那是一个 LLM 判断，同一份输入算两次会得到两个哈希。我们曾把那条线的定义平移到 CIRCE，从而凭空造出一个「确定性关口」并为一个不存在的问题设计了三套方案。这个错误后来被记为一条可执行检查（§3.1）。

### 1.4 贡献

- **方法**：三个「看起来有效、实测无效」的检查，及其识破方式（§3）；以及同类失效在产出本文档时的两次重演（§6.2.1）。
- **系统**：可靠性的四件缺一不可（§4）。
- **概念**：区分结构性不可替代性与能力性不可替代性，并证明它不能被两两合成的公式表达（§5）。
- **贯穿结构**：十二次同形及其理论锚点（§6）。
- **负面结果**：四个，包括一次未能完成的对照实验（§7）。

## 二、系统

### 2.1 三个端点

```
① Readiness Probe     「你现在能接活吗」—— 便宜，刻意不返回核剖面
② Core Profile Query  「删掉你，我会失去什么」—— 剖面 + VC + 链尾
③ Trust Update        「我刚调用过你，结果是这样」—— 追加账本
```

**①② 不能合并**：探活要能高频调用。把它做成「顺便返回核剖面」会让每次探活都背上签名与账本写入的代价。我们在实现里把这个区分写成了一条可测断言（`"profile" not in response`）。

**协议不选边**：核剖面的提供者被抽成 `CoreProfileProvider` 接口，所以「谁来算剖面」与「怎么传剖面」是分开的。

### 2.2 核剖面：确定性统计

| 维度 | 定义 | 需要 LLM？ |
|---|---|---|
| **深度** depth | 被调用时处于调用栈第几层 | ❌ |
| **密度** density | 调用频次 + 成功率 + 平均耗时的合成 | ❌ |
| **跨度** span | 被多少个不同 caller 调用过 / 跨多少种任务 | ❌ |

三维都是 [0,1] 的有界量，由饱和函数 x/(x+k) 归一化。

**我们选择 x/(x+k) 而非 1-exp(-x/k)**：后者需要 exp，而 exp 的最后一位随 libm 实现而变——链上锚定的量不该依赖 libm 的实现细节。x/(x+k) 只有一次除法。

**每个值都可手算核对**：`explain()` 返回的解释串把 `round(..., 6)` 一并写出，使「人手算的结果」与「系统值」**逐位闭合**。

> 这一条最初没做到：由于维度值经过 `round(..., 6)`（为保证 core_hash 稳定）而解释串显示未 round 的算术，两者相差 4.156e-7。这个差不会让任何人误判，**但它让「可复核」这句话不成立**——解释串的意义就在于逐位闭合，差最后一位就已经不是解释了。

### 2.3 自动增量

```
每次调用后  → 生成核探测凭证（VC）
           → 追加到被调用方账本（仅追加）
           → 核剖面按时间衰减加权重新计算
           → 新剖面对外广播
           → 技能条件化矩阵 R(i|k) 同步更新
```

**账本是真相来源，剖面是它的派生缓存。** 这一点在实现时被违反过一次（§4.4）。

### 2.4 MCP 集成

CIRCE 被实现为一个**零依赖的 MCP stdio 服务器**，暴露四个 tool：

```
circe_readiness_probe     circe_core_profile_query
circe_trust_update        circe_ledger_verify
```

**第四个是端到端实验逼出来的**（§4.3）。

**为什么零依赖**：本机既无 mcp Python 包也无 Node SDK，而 MCP 的 stdio 传输就是「一行一个 JSON-RPC 2.0 消息」——不需要库。**依赖越重，「这条通道能通」这个结论就越依赖环境，越不像在证明协议本身。**

## 三、主贡献一：三个「看起来有效、实测无效」的检查

**这一类内容对本领域最有价值，也最少被报告。** 一个不会失败的检查，与一个看起来会失败的检查，都比没有检查更危险。

### 3.1 从事故到规则：同名不同层

**事故**：我们把另一条线上「核剖面需要 LLM 判断」这一定义平移到 CIRCE，从而造出一个「核剖面不确定 → core_hash 不稳定 → 哈希链会断」的问题，并为它认真地设计了三套方案、写了三条代价、请人裁决。

**它为什么是假门**：

```
另一条线的核剖面：对一份【文本 / 概念图】做删除测试   → 需要 LLM
CIRCE 的核剖面  ：对一个【agent 的调用历史】做统计   → 不需要 LLM
                        名字相同，对象不同
```

**制度化**：事后仅把教训写进文档是**被动规则**——只有已经犯了错才会想起来。所以我们把它变成**结构化数据 + 可执行检查**（`glossary.py` + `check_conventions.py`）：

```
① 术语借用声明   引入同名术语的文件必须声明与另一条线的差异
                 glossary 里两侧 needs_llm 必须「有记录且不同」
② 禁用短语       只在另一条线语境里成立的说法不得出现在 CIRCE 里
                 （区分「主张」与「引述」——记录这个错误的文字本身不算违规）
```

**第二次检查覆盖 140 条短语。** 而它的规则经过三轮精确化：**第一版报了 13 处假警报**——而「报警变噪声、噪声变忽略」比没有检查更糟。**所以改的是规则精度，不是把检查关掉。**

**这一节的意义超出 CIRCE 本身**：它展示了一个从「事故」到「规则」的完整路径——不是把教训写进文档，而是把它变成可执行、可复现、可演进的检查。

### 3.2 一个筛模型的工具：它筛不出它想筛的东西

**背景**：第一次生态实验发现某个模型从未产出合法 JSON，于是加了 `--check-models`，用简单 prompt 先筛一遍。

```
筛模型（简单 prompt）:      然后进入真实决策:
  qwen3-vl:8b      可用       agent-A: 不行动（没能解析出 JSON（370 字符））
  qwen2.5:7b       可用       agent-C: 不行动（没能解析出 JSON（389 字符））
  deepseek-r1:14b  可用
```

**两个通过筛选的模型，在真实决策里失败了。**

**原因**：筛选 prompt 与真实决策 prompt **复杂度差一个量级**——前者只有一个短句，后者含人格、目标、工具表、核剖面块、历史。

**修法**：筛选必须用**与真实任务同构的 prompt**。

```
筛模型（同构 prompt）:
  qwen3-vl:8b      不稳定（0/2）   ✓ 正确识别
  qwen2.5:7b       可用
  deepseek-r1:14b  不稳定（0/2）   ✓ 正确识别
```

**同一个工具，换成同构 prompt 后立刻筛对了。** 上一轮我们写「它筛不出它想筛的东西」——**那句话对，但结论不是「筛模型没用」，而是「筛选必须测同一件事」。**

### 3.3 一个未解的观察，以及它暴露的方法论问题

**现象**：用 tool calling 决策时，24 次里 18 次返回**空响应**（`content=''` 且 `tool_calls=[]`）。

**三个诊断，三个否证**：

| 假设 | 怎么测 | 结果 |
|---|---|---|
| num_predict=200 太小 | 200 / 1024 / 不设 | **全部成功** ✗ |
| prompt 太长 | 打印实际 prompt | **只有 233 字符** ✗ |
| 快速连续请求 | 串行+间隔 / 串行无间隔 / 并发 4 路 | **全部 0/4 空响应** ✗ |

**而诊断过程暴露了一个方法论问题**：

> **前两个诊断脚本用的是我们手写复制的 prompt。**
> 于是它们一直在测一个「与真实运行近似但不相同」的东西——
> **而「真实 prompt」这个说法本身从未被核对。**

第三个诊断改成 `import` 任务里真正的函数，才看到它只有 233 字符。

**这与本文那条主线索同形**：一个层次的结论依赖于另一个层次上一个未经核对的假设。当时的假设是「我复制的 prompt 就是真的那个」。

我们把它记为**未解观察**，而不是解决它——因为三个假设被否证、单次调用成功、而实验里 25% 的这个不一致本身是数据，但它属于 **AI 行为科学**，不属于 CIRCE 的内核（见 §7.2）。

## 四、主贡献二：四件缺一不可

本节的结构：先给出四件的汇总表（§4.1），再逐个展开（§4.2–4.4）。读者需要先看到全景，才能理解每个洞的意义。

### 4.1 汇总：四件缺一不可

| 洞 | 在一个层次上做对了什么 | 但这个正确性依赖于 |
|---|---|---|
| 一 | 哈希链保证链内自洽 | **链尾的真实**（链尾可被重算） |
| 二 | 签名保证凭据不可伪造 | **端点的诚实**（端点签了个没变的尾） |
| 三 | 解释串让值可手算核对 | **输出的精度**（差了最后几位） |
| 四 | 账本记录了每次调用 | **剖面从账本重算**（写了却没读回来） |

四件对应四道防线：

```
哈希链（链内自洽）
    + 链尾外部锚定（防重算）
    + 签发前自校验（防「锚了个没变的尾」）
    + 签名（防伪造锚点）
    = 可靠性
```

**缺任何一件，可靠性都会在一个特定的位置断裂。** 而断裂的方式，都是「一个层次的正确性依赖于另一个层次上没有被保证的东西」。

### 4.2 洞一：哈希链防伪造，但不防重算

$$H_t = \mathrm{Hash}\bigl(H_{t-1} \;\|\; \mathrm{CoreProfile}_t \;\|\; \mathrm{Timestamp}\bigr)$$

**分段必须无歧义**：直接用分隔符会与内容里出现的同一字符混淆，所以每段先带长度前缀。

自检里有一条是这样写的：

```
✓ 重算整条链后自身自洽（所以必须锚定链尾）
```

**「篡改历史必须重算整条链，而这在算力上是不可能的」——这句话防伪造，但不防重算。** 重算一条账本只是一次循环，**新链自己校验是通过的**。

**补上的是**：把**链尾哈希写进链外凭证**（VC 的 `credentialSubject.ledgerHead`）。重算出的新链尾与已签凭证里的旧链尾对不上，**而改凭证需要私钥**。

### 4.3 洞二：只锚链尾也不够

`ledgerHead` 是**最后一条的 hash**。于是：

```
改第 1 条的内容，不重算          → 链尾【不变】
查询端点用这个没变的链尾签发凭据  → 调用方验签【通过】
```

**调用方看到 verified=True，而服务方的历史已经被改过。**

**根因不在链，在端点**：**签发前没有校验自己的账本。** 修法是签发前先 `verify()`，失败则**拒签并返回 409**——**而不是签一份「看起来有效」的凭据**。

**为什么必须用 409 而不是 200 + 空**：调用方要能区分「**peer 不在**」与「**peer 在，但它的话不可信**」。**把两者混为一谈，会让一个被篡改的 peer 与一个下线的 peer 得到同样的处理。**

**这个洞催生了第四个 MCP tool `circe_ledger_verify`。**

### 4.4 洞三与洞四：从自指测试到真实交互

**洞三：解释串与维度值差最后几位。**

维度值经过 `round(..., 6)`（为保证 core_hash 稳定）而解释串显示未 round 的算术，两者相差 4.156e-7。修法是把 `round(..., 6)` 一并写进解释串，并额外给出 `check` 字段供程序化核对。

**这个差不会让任何人误判，但它让「可复核」这句话不成立。** 解释串的意义就在于逐位闭合。

**洞四：自动增量断了。**

用两个真实本地模型跑完之后：

```
③ 用真实日志独立算：density = 0.547333   ← 有值
④ 查询端点返回：    density = 0.0        ← 白纸，而账本已有 6 条
```

**「自动增量」名义上实现了，实际断了**：`current_profile()` 返回的是注入的固定值，而 `update()` 写进账本的记录**没有回到剖面计算里**。

**为什么 76 项自指测试一条都没抓到**：`tests/` 里的 provider 与账本**从不同时使用**——provider 是静态的，账本是分开测的。**只有当真实调用真的走完整条链（模型回答 → Trust Update → 再查询）时，两者才第一次相遇。**

**修法**：`current_profile()` 改为**从账本重算**。配套要改三处——**账本条目必须写下重算所需的全部字段**（`callee`、`stack_depth`）。

**`stack_depth` 必须由 caller 给**：只有 caller 知道自己在哪一层发起调用，被调用方看不到。

### 5.1 一个被实测推翻的度量

我们在一个固定配对的生态里（每个 agent 有固定的调用对象）测到：

```
agent-A  span=0.226   被调用 3 次   被 1 个 caller
agent-B  span=0.167   被调用 1 次   被 1 个 caller
agent-C  span=0.167   被调用 1 次   被 1 个 caller
```

**每个被调用者只有一个 caller——span 结构上无法分化。**

而这不是 span 失灵：**它的动作是正确的**（span 序与真实 caller 数序完全一致）。**问题是它测的东西**：

> **CIRCE 原先的 span 测的是「被调用分布」，不是「不可替代性」。**
> 一个 agent 在固定配对的生态里 span 很高，**但那可能只是被结构性地锁定了**——caller 没有别的选择，而不是它真的独特。

### 5.2 形式化

设 agent $X$ 的调用记录集为 $R_X$，每条记录含 $(\text{caller}, \text{task})$。定义

$$
C = \bigl|\{\, r.\text{caller} : r \in R_X \,\}\bigr|, \quad
T = \bigl|\{\, r.\text{task} \phantom{.} : r \in R_X \,\}\bigr|, \quad
P = \bigl|\{\, (r.\text{caller},\, r.\text{task}) : r \in R_X \,\}\bigr|
$$

**诊断量**为每 caller 平均任务数 $\tau = P / C$：

| 情形 | 含义 |
|---|---|
| $C > 1$ 且 $\tau \approx 1$ | **结构性锁定嫌疑**：多个 caller，但每个都只在同一件事上找我 |
| $\tau \gg 1$ | **能力性证据**：每个 caller 在多件事上依赖我 |

### 5.3 关键结论：任何两两合成的公式都分不开

考虑两个情形：

$$
\begin{aligned}
P &: \text{caller}_1 \text{ 做任务 } A,\; \text{caller}_2 \text{ 做任务 } A
     &&\Rightarrow C=2,\; T=1,\; P=2 \\
Q &: \text{caller}_1 \text{ 做任务 } A,\; \text{caller}_1 \text{ 做任务 } B
     &&\Rightarrow C=1,\; T=2,\; P=2
\end{aligned}
$$

**$P$ 与 $Q$ 的不可替代性含义完全相反**（$P$ 是结构性嫌疑，$Q$ 是能力性），但：

| 公式 | $P$ | $Q$ | 能否分开 |
|---|---|---|---|
| 原始 span：$\bigl(\mathrm{sat}(C) + \mathrm{sat}(T)\bigr) / 2$ | 0.22619 | 0.22619 | **✗ 对称，分不开** |
| 提议的 span_by_task：$\mathrm{sat}(P)$ | 0.074074 | 0.074074 | **✗ 合并，也分不开** |

**两个公式都分不开，原因不同但结果相同**：原始公式对 $C$ 与 $T$ **等权平均**（对称），提议公式把两者**合并成配对数**（丢掉了区别）。

> **所以修正不是「换公式」，是「别把三个量合成一个」。**

我们据此实现的 `span_decomposed()` 返回三元组与诊断，而不是一个标量。**这是一个度量设计上的教训**：当一个量承载了两种相反的含义时，把它合成一个数不会「更方便」，只会让两种含义都无法被读出。

### 5.4 H=0 的两种解释

在任务多样性实验（专家 / 通用 × coding / writing）中，我们测到：

```
general-C   coding:  H=0.811  {expert-A: 3, general-D: 1}
            writing: H=0.000  {expert-B: 3}
```

按「H=0 表示结构性锁定」的直觉读法，这里会得出错误结论——general-C 在 writing 上只调 expert-B，**而那正是能力性选择**（expert-B 是 writing 专家）。

**所以 H = H(callee | caller, task) = 0 有两种解释：**

| H=0 的含义 | 判别依据 |
|---|---|
| **结构性锁定** | 候选集里**没有**别的选择 |
| **能力性锁定** | 候选集里**有**别的选择，但一个明显更好 |

**区分它们需要第二维：能力对齐度**（被选中的 callee 在该 task 上是否真的更强）。**「偏好 + 对齐」才是能力性不可替代性；只有偏好可能只是乱挑。**

## 六、同一形状的十二次出现

### 6.1 理论锚点

本节与**构念效度**（construct validity）研究直接相关。Kearns（arXiv:2602.15532）明确提出：LLM 评测中的核心问题是构念效度——一个基准测的**是不是它声称在测的东西**。Alaa 等（arXiv:2503.10694）在医疗基准上给出了同方向的论证。

**本文的三个失效本质上都是构念效度问题**：

| 检查 | 它声称在测 | 它实际在测 |
|---|---|---|
| 术语检查（第一版） | 术语借用事故 | 术语**出现**（含引述），13 处假警报 |
| 筛模型（第一版） | 模型能否完成**本任务** | 模型能否输出 JSON（**一个更简单的任务**） |
| 诊断（前两个） | 真实运行的行为 | **我复制的 prompt** 的行为 |

我们把它写成一条可执行规则：

> **任何验证脚本都必须声明「它测的东西与真实运行的东西在哪一点上是同一个」。**

### 6.2 十二次同形

**系统层（五次）**：

| 洞 | 在一个层次上做对了什么 | 但这个正确性依赖于 |
|---|---|---|
| 一 | 哈希链保证链内自洽 | 链尾的真实 |
| 二 | 签名保证凭据不可伪造 | 端点的诚实 |
| 三 | 解释串让值可手算核对 | 输出的精度 |
| 四 | 账本记录了每次调用 | 剖面从账本重算 |
| 五 | 核剖面由调用日志的**确定性统计量**算出 | **输入的受控性**（`skill` 是调用方自由文本，直接进 `span`） |

**验证层（三次）**：

| 检查 | 它做对了 | 但它依赖于 |
|---|---|---|
| 术语检查（第一版） | 能抓同名不同层的用法 | **引述与主张的区分** |
| 筛模型（第一版） | 能测「模型会不会输出 JSON」 | **筛选 prompt 与真实任务同构** |
| 诊断（前两个） | 能复现一个 prompt 的行为 | **那个 prompt 就是真的那个** |

**还有一层，在工程实现与文档产出里（四次）**：

> **三张表的小计写在这里，是为了让 `5 + 3 + 4 = 12` 可以当场核对。**
> 这一节原先只给前两张表标了数，第三张没标——于是**表里实际有 11 行而正文写「十次」**
> 这件事一直没有被看见。**一个不能当场核对的小计，就是一个不会被发现的错。**

| 项 | 做对了 | 依赖于 |
|---|---|---|
| MCP 自检 | 分发逻辑对 | 管道能通（stdout 纯净、flush、编码） |
| PDF 公式自检（第一版） | 能查「美元符号有没有配对」 | **检查必须在信息被销毁之前做** |
| PDF 中文校验（前两版） | 能回答「文件生成了吗」 | **检查方法与 PDF 的真实编码一致** |
| **MCP 挂载** | **配置写对了** | **协议版本兼容** |

#### 洞五：核剖面的确定性，依赖于调用方输入字段的受控性

`span` 的一个输入是「跨多少种任务类型」，即 `len({r.skill for r in rs})`——
而 **`skill` 是调用方自报的自由文本**，schema 里既没有词表，也没有示例。

`span = (sat(callers, 5) + sat(skills, 5)) / 2`，其中 `sat(x, k) = x / (x + k)`。于是：

| 情形（同一个 agent、同一个 caller、各记录一次） | span |
|---|---|
| 1 个一致的 skill | 0.166667 |
| 3 个噪声 skill | 0.270833（**×1.625**） |
| 5 个噪声 skill | 0.333333（**×2.0**） |

**而噪声只会单调抬高 `span`**——技能种类数不会因为「填错了」而减少。

**其中一次不是在受控实验里发生的**（2026-10-12）。把一个**前沿模型**（`gpt-6-luna`，
经 GitHub Copilot 驱动）放在一个**第三方 MCP 客户端**（VS Code Copilot CLI 1.0.92，
客户端标识 `copilot-cli`）的调用方位置上，只给它一句普通指令去记录一次调用。
它填的 `skill` 是「检索」——而账本里已有的技能是 `qa`：

```
记录前:  skills = {'qa'}          → span = 0.166667
记录后:  skills = {'qa','检索'}   → span = 0.226190     （×1.357）
```

**一次普通调用，核剖面一个维度涨 35.7%，纯粹因为换了个名字。**
没有人要求它填哪个词——**它只是照自己的理解填了一个合理的名字。**

这条与上表那两行的差别不在幅度（×1.357 比 ×2.0 小），而在**性质**：
上表是构造出来的（我拿三个本地模型强制各记录一次），
**这一条是现场发生的**——真实客户端、前沿模型、一条正常指令，
而且**归一的边界也当场被验证了**：账本里存的仍是原话 `"skill": "检索"`。

**为什么会填错**：把三个本地模型放到调用方的位置上，同一个 agent、同一个 caller、各记录一次，
它们填出了三个不同的值（`core_profile_query` / `circe` / `general`）。
**它们不是在犯错——描述里没有它们能对齐的词表，它们只能猜。**

**修法与另外四条同形：把那个未被保证的东西补上**——受控词表，或把词表外的值归一到
`unspecified`。而修的时候有一条必须守住：**归一只发生在派生统计层，账本里仍写调用方原话**
——账本是真相来源，剖面是它的派生缓存（这正是洞四修好之后才立得住的分工）。
实测：`--selftest` 从 52 项增至 66 项，新增的断言里最关键的一条是
「**账本里仍是调用方原话，不是归一后的桶名**」。

**而这条修法在真实链路上也验过**（2026-10-12）：把 `--skill-vocabulary` 设成 `qa,检索`，
再让同一个第三方客户端（VS Code Copilot CLI + `gpt-6-luna`）记录两个新技能名
（「翻译」「摘要」）。结果：

```
span = 0.270833     ← 若不传词表则为 0.305556（预测先行，实测命中）

账本里的原话（4 种）: qa, 摘要, 检索, 翻译       ← 一字未改
剖面的桶名（3 种）  : qa, unspecified, 检索      ← 2 个噪声名 → 1 个桶
```

**也就是说：N 个噪声名归进 1 个桶，而不是 N 个桶。** 而归一的边界当场被两端同时验证了——
账本侧留着原话，剖面侧给出桶名，**而且那个调用方自己发现了这个不一致并如实报告**。

**两条必须说清的边界**：

**① 它不在 §4 那条防线链上。** §4 的四件（哈希链、链尾外部锚定、签发前自校验、签名）
是**可靠性的四道防线**，缺一件就在特定位置断裂。洞五不是第五道防线——
它是**同一个形状在另一处的出现**：一个统计量的正确性，依赖于它没在管的东西。
把两者混为一谈会造出一个「五件缺一不可」的假结构。

**② 它与洞四是一对，而不是两条独立的洞。** 两条都只在**另一端坐着一个真实的模型**时
才显形：洞四是「账本写了，剖面没读回来」，自指测试里 provider 与账本从不同时使用，
所以 §4.4 记的那一批自指测试一条都没抓到；洞五是「剖面算对了，可算它的那个字段没人管」，
`StatsProvider` 的单测全部通过，因为测试自己挑的 `skill` 一直是一致的。
**同一个方法论缺口，在两个相邻的层次上各出一次。**

**而这正好是本文开头那句话的继续**：本文记录的不是一次成功的设计，
而是一个工程在实测中被反复推翻的过程。**洞四与洞五都不是我想出来的，
是把真的模型接到另一端之后，它替我照出来的。**

### 6.2.1 第九至第十二次：产出与集成时的同形

**第九次（MCP 服务器的自检）**：

进程内直接调分发函数的自检**全部通过**——它证明的是「分发逻辑对」。
而 stdio 传输有一批只在**真实管道**里才暴露的东西：

```
stdout 混入非协议输出（调试 print、库的 banner）→ 客户端解析失败
没有 flush                                      → 客户端永远等不到响应
行缓冲 / 编码问题                                → 中文乱码
子进程启动失败但父进程不知道
```

**分发逻辑对 ≠ 管道能通。** 修法是补一个真的起子进程、真的走管道的往返测试。

**第十次（在 `tools/md_to_pdf.py` 的注释里）**：

> A first version of this self-check inspected the finished HTML instead, found 232 …
> **Checking after the information is destroyed is not a check.**

即：第一版自检去查**渲染完成后的 HTML**，那时公式已被 MathJax 消费、
公式定界符与源码的对应关系已经不存在，**232 处误报**。正确位置是**转换之后、渲染之前**。

**第十一次（生成这份 PDF 时，同一形状连犯两次）**：

| 尝试 | 它做了什么 | 为什么错 |
|---|---|---|
| 在内容流里找 `"核剖面".encode("utf-16-be")` | 命中 0/6 | **PDF 里 CJK 用 CID 编码，内容流里是字形索引，不是 Unicode** |
| 用 Chrome `--screenshot` 渲染 PDF | 得到纯黑图 | **headless Chrome 不加载 PDFium 插件** |

**两次都把「我的检查方法错了」读成了「内容错了」**——
直到改成解析 **`/ToUnicode` CMap**（PDF 为「可复制文本」必须携带的映射表），
才得到正确结论：**636 个汉字，10/10 探针命中。**

> **这与 §6.1 那条规则是同一件事，但它把规则的适用范围扩大了一层**：
> 不只是「验证脚本要测同一个东西」，而是
> **「一份产出物的校验，必须用那份产出物自己的编码去问」**——
> 否则检查的失败会伪装成内容的失败。

**第十二次（把 CIRCE 挂到真实 MCP 客户端时）**：

| 项 | 做对了 | 依赖于 |
|---|---|---|
| **MCP 挂载** | **配置写对了** | **协议版本兼容** |

**这一次与前十一次的差别在于：它不是一个 bug，是一个策略的隐含条件被撞开了。**

前十一次都是「某处做对了，但依赖另一处没保证的东西」——
而这一次，**「成为现有协议上的一个服务」这个策略本身**里就藏着一个未被写出的前提：
**对方不只是「会这个协议」，还得「与你的版本兼容」。**

详细经过与抓到的原始协议序列见 §8.2。**它的形状与前十一次完全一致**：

```
「配置写对了」          ← 这一层是对的（code --add-mcp 成功、~/.claude.json 内容正确）
「所以挂载会成功」      ← 这个推论依赖【协议版本兼容】
                          而那个条件在 MCP 上是每几个月变一次的
```

**而它失败的样子极具误导性**：客户端报连接错误 → **看起来像配置写错了** →
于是排查方向是检查 JSON、路径、权限——**而真因在协议版本上**。


### 6.3 同一条修法

十二次的修法都是同一条：**把那个未被保证的东西补上**——链尾外部锚定、签发前自校验、逐位闭合、从账本重算、**受控词表（或归一到 `unspecified`）**、引述与主张的区分、筛选 prompt 同构、诊断用真实函数、stdio 往返测试、自检放在信息销毁之前、校验用产出物自己的编码、**核实对端的协议版本**。
而它们指向同一件事：

> **每一层都在试图消除前一层的不确定性，然后引入自己的。**
> 修到洞三时已经没有下一层可推——**它就是最后一位**。

这与本项目在别处反复遇到的那条线是同一件事：**任何测量都会偏离，因为中介的参数会进入结果。** 哈希链是中介，端点是中介，解释串是中介，账本与剖面之间也是。

> **在多层验证系统中，不确定性不会被消除，只会被推向下一层。**
> 修到最后一层时，它已经无法再被推——**那就是系统的精确边界。**

## 七、负面结果

我们报告四个，因为它们**限定了结论的适用范围**。

### 7.1 未能完成的对照实验

**要回答的问题**：给 agent 看剖面但不给任何倾向性提示，它会不会**自发**支持一个剖面为空的新加入者？

**实测**：

```
4 个 agent × 4 次决策 = 16 次
call=4, no_action=12      ← 12 次「没能解析出 JSON」
```

同一个 `qwen2.5:7b`，在较简单的决策 prompt 下能稳定产出 JSON，在含剖面块的 prompt 下不能。

**换成 tool calling 也没有解决**（25% 成功率，18 次空响应，见 §3.3）。

> **要区分「剖面进入决策输入」与「剖面改变了偏好」，前提是模型能稳定产出决策——而它做不到。**
> **这是能力的下限，不是实验设计的缺陷。**

我们把它记为**未解观察**，而不是解决它——因为：

> **CIRCE 的设计哲学是「判断留在链外」。** 链上只记录事实。
> **LLM 在调用方的决策过程是黑箱，这是有意的，不是缺陷。**
> 所以拿不到这个对照，CIRCE 仍然成立；那属于 **AI 行为科学**，不属于 CIRCE 的内核。

### 7.2 白纸问题没有自然解决

**新加入者（账本为空）在单阶段实验里被调用 0 次。** 没有任何 agent 去调用一个剖面为空的新加入者。这是**冷启动问题的直接呈现**。CIRCE 的设计承认它（查询在账本为空时返回 warning 而不是假数据），但不解决它。

**两阶段实验里它被调用 2 次**——但那是**被提示的结果**（prompt 里写了「也可以选择支持还没被调用过的」），**不是自发行为**。

### 7.3 结构性的实验限制

**固定配对让 span 无法分化**：在固定配对的生态里，跑多久都不会。任务多样性实验打破了它（专家在强项上被调用 5:1 和 1:7）。

**时间衰减的真实尺度给不出**：运行时长在秒级，半衰期（默认 30 天）内的衰减 ≈ 1.0。要测真实尺度需要跑几小时到几天。

**实验规模小**：最多 5 个 agent、每种配置几轮。这足以暴露结构性问题，不足以给出统计结论。

## 八、相关工作

**元数据取自 arXiv 官方 API**（`tools/fetch_related_work.py`），不依赖作者记忆。

### 8.1 agent 声誉与信任

多智能体系统中的信任建立已被系统综述。近年针对 LLM 多智能体的工作包括 MiniRep（arXiv:2609.39297）、DART（arXiv:2609.05529）、DRF（arXiv:2509.05764）。

**与 CIRCE 的差别在问法上，不在机制上**：这些系统输出的是**可信度**——一个关于目标的、可以被聚合的成分；CIRCE 输出的是**不可替代性**——一个关于**关系**的量，因此它的查询接口必须带 `caller`。**一个高声誉的 agent 可能完全可替代，而一个低声誉的 agent 可能是某个 caller 的唯一选择。**

### 8.2 互操作协议

agent 协议已有一份覆盖 MCP / ACP / A2A / ANP 的综述（arXiv:2505.02279），IETF 亦在推进用例与需求文档。

**CIRCE 不在这一层竞争**——它是一个**服务**，不是协议（§2.4）。**这是设计选择而非能力限制**：新造一个信任协议意味着要求对方先学会它，而挂在 MCP 上意味着对方已经会了。

> ⚠️ **上面那句话有一个隐含条件，而我们在实测中撞上了它**（2026-10-10）。
>
> **「挂在 MCP 上意味着对方已经会了」——前提是协议版本兼容。**
> 这个条件在快速演进的协议里**不是自动满足的**。
>
> MCP 从 `2025-06-18` 到 `2026-07-28` 有九个 breaking change，
> 其中一条把 `initialize` 握手整个删除、改为无状态的 `_meta` 传版本，
> 并新增 `server/discover` 为 MUST。**而 CIRCE 原本的实现停在 `2025-06-18`。**
>
> 当我们把 CIRCE 挂到真实的 **Claude Code 2.1.296** 上时，
> 用录制代理（`tools/mcp_recording_proxy.py`，透明中转、不改一字）
> 抓到它实际发的第一条请求是：
>
> ```
> C→S  {"method":"server/discover",
>       "params":{"_meta":{"io.modelcontextprotocol/protocolVersion":"2026-07-28",
>                          "io.modelcontextprotocol/clientInfo":
>                            {"name":"claude-code","version":"2.1.296"}}}}
> S→C  {"result":{"protocolVersions":["2026-07-28","2025-11-25","2025-06-18"],
>                 "resultType":"complete", ...}}
> C→S  {"method":"initialize","params":{"protocolVersion":"2025-11-25", ...}}
> S→C  {"result":{"protocolVersion":"2025-11-25", ...}}
> C→S  {"method":"notifications/initialized"}
> C→S  {"method":"tools/list"}
> S→C  {"result":{"tools":[四个工具], "resultType":"complete", ...}}
> ```
>
> **它在探测**：先按新协议发 `server/discover`，拿到我们的版本列表后
> **回退到旧握手用 `2025-11-25`**。两代都被兼容层接住了。
>
> **如果没加兼容层，第一条请求就会失败**——而失败的样子会是客户端报连接错误，
> **看起来像配置写错了**。
>
> **所以「成为现有协议上的一个服务」这个策略的成立条件，比它的表述更严**：
> 它要求的不只是「对方会这个协议」，而是「**对方的协议版本与你的兼容**」。
> 在一个每几个月就有 breaking change 的协议上，
> **这是一项持续的维护义务，不是一次性的集成工作。**

> ⚠️ **同一句话还有第二个隐含条件，而它在第二个客户端上才撞上**（2026-10-11）。
>
> **「对方已经会了」的精确范围是：对方会的是 MCP 协议本身。**
> 但它对**你起的工具名**有它自己的约束，而**那条约束不在 MCP 规范里**。
>
> 我们原本用 `circe.` 做工具名的命名空间（**MCP 不禁止 `.`**）。
> 把 CIRCE 挂到 **VS Code 1.141.0** 上时，它确实连上了、握了手、
> 还**准确地发现了四个工具**——然后：
>
> ```
> [info]    Discovered 4 tools
> [warning] Tool "circe.readiness_probe" is invalid. Tools names may only contain [a-z0-9_-]
>           （同一条警告共四条：四个工具全部被判为无效）
> ```
>
> **可用工具数 = 0。** 约束的来源是 **LLM 侧 function name 的模式 `[a-z0-9_-]`**——
> 工具名是**给模型看的标识符**，所以那条模式是承重的，而它**不在 MCP 规范里**。
>
> **而这条只在第二个真实客户端上才显形**：自检、管道往返、以及第一个真实客户端
> （Claude Code 2.1.296——**它接受带点号的名字**）**全都不会报**。
> 我最初只在 Ollama 上测了这道缝、得到「接受」，便写成「这道缝不存在」——
> **把「我测的那个客户端接受」读成了「不存在这道缝」，正是 §6.1 那条规则。**
>
> **修法**：四个工具名改为 `circe_readiness_probe` 一类（落在 `[a-z0-9_-]` 内），
> 并在自检里加一条断言，让不可移植的名字**无法被写回来**。
>
> **验证（真实客户端，可证伪）**：改完在客户端里 Stop → Start 一次，
> 同一条日志的**最近一次连接**给出 `Discovered 4 tools`，**且一条 `is invalid` 都没有**。
> **所以「点号是唯一的问题」这个假设成立**——若重启后仍有 `is invalid`，它就被推翻。
>
> **所以那句话现在要读成：能连上 ≠ 能用。**

> 📌 **顺带抓出的一个真 bug**（同一个代理的副产物）：
> 初版的 `_ok()` 只从 `_meta` 读版本号，而**旧协议把版本放在 `params.protocolVersion`**。
> 于是 `initialize` 的应答里 `result.protocolVersion = 2025-11-25`（对）
> 而 `_meta.protocolVersion = 2025-06-18`（错）——**同一个响应给出两个版本号**。
> 客户端没在意（它继续握手了），但那是真的不一致。
> **而这个 bug 只在真实客户端的真实序列里才暴露**：
> 我自己写的 `demo_mcp_client.py` 从来不同时发两代握手，所以永远碰不到它。

### 8.3 可验证凭证与 agent 身份

W3C 已成立 **Agent Identity Registry Protocol** 社区组，学界亦有结合零知识证明的去中心化身份协议（DIAP，arXiv:2511.11619）。

**CIRCE 的实现直接使用 Ed25519 + W3C VC 数据模型**，不重新发明签名与凭证格式。**我们贡献的是它们承载什么**：凭证里锚定的是**账本链尾**，而 §4.2–4.3 说明**这个锚定位置的选择本身就是安全性的一部分**。

### 8.4 抗女巫与「多个不等于多份」

Bara（arXiv:2609.01873）指出：**增加 agent 数量不等于增加证据量**。Shi 与 Joo（arXiv:2510.27554）从服务发现角度处理同一问题。

**这与本文 §5 同源**：如果 k 个 agent 都只是同一个底层能力的复制品，那么「被 k 个不同 caller 调用过」与「被 1 个 caller 调用 k 次」在**不可替代性**上没有区别。**CIRCE 的 `span_decomposed` 三元组可以看作这个观察在度量层的一个具体后果**：只有把 C、T、P 分开看，才能问出「这些 caller 是不是**独立地**需要我」。

## 九、局限与边界

1. **核剖面测的是「被调用分布」，不是「不可替代性」。** §5 给了区分的工具（`span_decomposed`），但**默认的 span 仍只测前者**。

2. **没有 ground truth。** 在生态里，「真实的不可替代性」没有定义。所以我们**不试图验证剖面是否正确**，只观察它是否稳定、是否分化、是否随时间演化。**稳定性本身就是信号。**

3. **判断在链外。** 这不是缺陷，但它意味着**链上的事实不能推出「应该调用谁」**——那需要调用方自己的模型。

4. **实验规模小。** 最多 5 个 agent、每种配置几轮。

5. **本地模型的能力下限限制了可做的对照。** 见 §7.1。

6. **一个被绕开的问题。** CIRCE 用调用历史替代了内容层面的测量。这是一个正确的转向（调用历史确定，内容判断不确定），**但它绕开而没有解决那个问题**。

## 十、结论

### 10.1 三个可交付物

**问法**：不问「你是否可信」，问「删掉你，调用方会失去什么」。这把信任从目标的属性变成关系的属性——**不可替代性不是某个智能体「拥有」的性质，而是它在特定 caller、特定任务、特定时刻所占据的结构位置。**

**分工**：判断留在链外，链上只记事实。这个分工让哈希链的输入是确定的，从而可被锚定。

**度量工具**：`span_decomposed` 三元组，区分结构性不可替代性与能力性不可替代性。**任何两两合成的公式都分不开这两种情形**——所以修正不是换公式，是别把三个量合成一个。

### 10.2 所以呢

**本文最有价值的部分不是系统建成了，是它在实测中被推翻了五次。**

所以，三句话：

1. **任何声称测量不可替代性的系统，都必须先证明它测的不是「被调用分布」。**
2. **任何基于哈希链的信任系统，都必须证明它在签发前校验了自己的账本。**
3. **任何自动化的检查，都必须证明它测的对象与真实运行的对象是同一个。**

三条规则里，前两条来自系统层，第三条来自验证层——**而第三条还多了一个推论**：一份产出物的校验，必须用那份产出物自己的编码去问。

**这三句话比 CIRCE 系统本身更可传递。**

### 10.3 一条贯穿全部的线索

> **一个层次的结论，依赖于另一个层次上一个未经核对的假设。**

哈希链依赖端点、端点依赖链尾、解释串依赖精度、账本依赖重算、剖面依赖输入的受控、诊断依赖「我抄对了」、筛选依赖「测的是同一件事」、挂载依赖「协议版本兼容」——**十二次同形**。

**每一层都在试图消除前一层的不确定性，然后引入自己的。** 修到最后一层时，它已经无法再被推——**那就是系统的精确边界**。

**这不是一个需要被消除的缺陷，是一个需要被认识的结构。** 在多层验证系统中，不确定性永远不会被消除，只会被推向下一层。而认识这个结构本身，就是本文的贡献。

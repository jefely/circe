# CIRCE：核不可替代性识别与持续评估

**——一个建立在「被调用历史」上的信任基础设施，以及它在实测中被推翻的四个假设**

> 状态：工作稿（v0.1）。内容来自工程实现与实测，不是设计推演。
> 所有数字与断言都在 `CIRCE/` 下可复现；八个验证入口合计 **200 项断言**。

---

## 摘要

我们提出 **CIRCE**（**C**ore **I**rreplaceability **R**ecognition and **C**ontinuous
**E**valuation，核不可替代性识别与持续评估），一个 AI-to-AI 信任基础设施。
它的核心主张是**换一个问法**：不问「你是否可信」，而问「**删掉你，调用方会失去什么**」。

与既有信任/声誉系统不同，CIRCE 的核剖面**完全由调用日志的确定性统计量得出**，
不含任何 LLM 判断——判断被有意留在调用方一侧、留在链外。
链上只记录事实：谁在何时调用了谁、结果如何。

我们报告三类结果。**第一类是概念上的**：实测显示 CIRCE 原先的 `span` 度量
**测的是「被调用分布」，不是「不可替代性」**——一个 agent 在固定配对的生态里
span 很高，但那可能只是被**结构性锁定**（caller 没有别的选择）。
我们给出 `callers / tasks / pairs` 三元组来区分**结构性**与**能力性**不可替代性，
并证明**任何两两合成的公式都分不开这两种情形**。

**第二类是系统上的**：可靠性的建立需要**四件缺一不可**的东西——
哈希链（链内自洽）、链尾外部锚定（防重算）、**签发前自校验**（防「锚了个没变的尾」）、
以及签名（防伪造锚点）。其中第三件是端到端实验才暴露的：**只锚链尾防不住中间改写。**

**第三类，也是我们认为对本领域最有价值的**：我们报告**三个「看起来有效、实测无效」的检查**，
以及它们被识破的过程。一个筛模型的工具用简单 prompt 时判定三个模型"可用"，
换成与真实任务同构的 prompt 后立刻判定其中两个"不稳定（0/2）"。
**这类失败在论文里很少被报告，但它们是自动化验证最大的风险来源**：
一个不会失败的检查与一个看起来会失败的检查，都比没有检查更危险。

我们同时报告四个负面结果，包括一次**未能完成的对照实验**——
不是因为设计有误，而是因为本地模型在含核剖面的 prompt 下无法稳定产出决策。
我们**把它记为未解观察，而不是解决它**。

## 一、引言

### 1.1 一个换掉的问法

AI agent 之间的信任通常被表述为「你是否可信」。CIRCE 把它换成：

> **「删掉你，调用方会失去什么？」**

这个替换不是措辞游戏，它改变了接口的形状：

- **可信度是目标的属性** → 调用方只能接受或拒绝
- **不可替代性是关系的属性** → 同一个目标对不同调用方可以有不同的值

因此 CIRCE 的查询请求必须带 `caller`，而返回的不是一个建议，是**统计量与凭据**。
**要判断「是否该依赖它」，那是调用方自己的事**——它可以用 LLM 读这份剖面、权衡、决定，
**而那一步不进链、不进 hash**。

### 1.2 为什么用调用历史而不是内容

CIRCE 的核剖面是调用日志的统计量（深度 / 密度 / 跨度），**不含 LLM 判断**。
这一选择有一个直接的工程后果：**哈希链的输入是确定的**，
同一份日志算两次得到同一个 `core_hash`，因此链可以锚定。

**这与本项目另一条线上的做法形成对照**：在一个基于文本的「删除测试」框架里，
核剖面需要对「删掉这个概念，文本结构会不会塌陷」作出判断——**那是一个 LLM 判断**，
同一份输入算两次会得到两个哈希。我们曾把那条线的定义平移到 CIRCE，
从而凭空造出一个「确定性关口」并为一个不存在的问题设计了三套方案。
**这个错误后来被记为一条可执行检查**（§6.1）。

### 1.3 贡献

1. **概念**：区分**结构性**与**能力性**不可替代性，并证明它不能被两两合成的公式表达（§3）。
2. **系统**：可靠性的**四件缺一不可**，其中「签发前自校验」是端到端实验暴露的（§4）。
3. **方法**：三个「看起来有效、实测无效」的检查，及其识破方式（§6）。
4. **负面结果**：四个，包括一次未能完成的对照实验（§7）。

## 二、系统

### 2.1 三个端点

```
① Readiness Probe     「你现在能接活吗」—— 便宜，**刻意不返回核剖面**
② Core Profile Query  「删掉你，我会失去什么」—— 剖面 + VC + 链尾
③ Trust Update        「我刚调用过你，结果是这样」—— 追加账本
```

**①② 不能合并**：探活要能高频调用。把它做成「顺便返回核剖面」
会让每次探活都背上签名与账本写入的代价。我们在实现里把这个区分
写成了一条可测断言（`"profile" not in response`）。

**协议不选边**：核剖面的提供者被抽成 `CoreProfileProvider` 接口，
所以「谁来算剖面」与「怎么传剖面」是分开的。

### 2.2 核剖面：确定性统计

| 维度 | 定义 | 需要 LLM？ |
|---|---|---|
| **深度** `depth` | 被调用时处于调用栈第几层 | ❌ |
| **密度** `density` | 调用频次 + 成功率 + 平均耗时的合成 | ❌ |
| **跨度** `span` | 被多少个不同 caller 调用过 / 跨多少种任务 | ❌ |

三维都是 `[0,1]` 的有界量，由饱和函数 `x/(x+k)` 归一化。
**我们选择 `x/(x+k)` 而非 `1-exp(-x/k)`**：后者需要 `exp`，
而 `exp` 的最后一位随 libm 实现而变——**链上锚定的量不该依赖 libm 的实现细节**。
`x/(x+k)` 只有一次除法。

**每个值都可手算核对**：`explain()` 返回的解释串把 `round(..., 6)` 一并写出，
使「人手算的结果」与「系统值」**逐位闭合**。

> 这一条最初没做到：由于维度值经过 `round(..., 6)`（为保证 `core_hash` 稳定）
> 而解释串显示未 round 的算术，两者相差 `4.156e-7`。
> 这个差不会让任何人误判，**但它让「可复核」这句话不成立**——
> 解释串的意义就在于逐位闭合，差最后一位就已经不是解释了。

### 2.3 自动增量

```
每次调用后  → 生成核探测凭证（VC）
           → 追加到被调用方账本（仅追加）
           → 核剖面按时间衰减加权重新计算
           → 新剖面对外广播
           → 技能条件化矩阵 R(i|k) 同步更新
```

**账本是真相来源，剖面是它的派生缓存。** 这一点在实现时被违反过一次（§4.4）。

### 2.4 MCP 集成

CIRCE 被实现为一个**零依赖的 MCP stdio 服务器**，暴露四个 tool：

```
circe.readiness_probe     circe.core_profile_query
circe.trust_update        circe.ledger_verify
```

**第四个是端到端实验逼出来的**（§4.3）。

**为什么零依赖**：本机既无 `mcp` Python 包也无 Node SDK，而 MCP 的 stdio 传输
就是「一行一个 JSON-RPC 2.0 消息」——不需要库。**依赖越重，
「这条通道能通」这个结论就越依赖环境，越不像在证明协议本身。**

## 三、主贡献一：两种不可替代性

### 3.1 一个被实测推翻的度量

我们在一个固定配对的生态里（每个 agent 有固定的调用对象）测到：

```
agent-A  span=0.226   被调用 3 次   被 1 个 caller
agent-B  span=0.167   被调用 1 次   被 1 个 caller
agent-C  span=0.167   被调用 1 次   被 1 个 caller
```

**每个被调用者只有一个 caller——span 结构上无法分化。**

而这不是 `span` 失灵：**它的动作是正确的**（`span` 序与真实 caller 数序完全一致）。
**问题是它测的东西**：

> **CIRCE 原先的 `span` 测的是「被调用分布」，不是「不可替代性」。**
> 一个 agent 在固定配对的生态里 span 很高，**但那可能只是被结构性地锁定了**——
> caller 没有别的选择，而不是它真的独特。

### 3.2 形式化

设 agent $X$ 的调用记录集为 $R_X$，每条记录含 `(caller, task)`。定义

$$
C = |\{\,r.\text{caller} : r \in R_X\,\}|, \quad
T = |\{\,r.\text{task} \phantom{.} : r \in R_X\,\}|, \quad
P = |\{\,(r.\text{caller},\, r.\text{task}) : r \in R_X\,\}|
$$

**诊断量**为每 caller 平均任务数 $\tau = P / C$：

| 情形 | 含义 |
|---|---|
| $C > 1$ 且 $\tau \approx 1$ | **结构性锁定嫌疑**：多个 caller，但每个都只在同一件事上找我 |
| $\tau \gg 1$ | **能力性证据**：每个 caller 在多件事上依赖我 |

### 3.3 关键结论：任何两两合成的公式都分不开

考虑两个情形：

$$
\begin{aligned}
P &: \text{caller}_1 \text{ 做任务 } A, \; \text{caller}_2 \text{ 做任务 } A
     &&\Rightarrow C=2,\; T=1,\; P=2 \\
Q &: \text{caller}_1 \text{ 做任务 } A, \; \text{caller}_1 \text{ 做任务 } B
     &&\Rightarrow C=1,\; T=2,\; P=2
\end{aligned}
$$

**$P$ 与 $Q$ 的不可替代性含义完全相反**（$P$ 是结构性嫌疑，$Q$ 是能力性），
但：

| 公式 | $P$ | $Q$ | 能否分开 |
|---|---|---|---|
| 原始 `span`：$({\rm sat}(C) + {\rm sat}(T))/2$ | 0.22619 | 0.22619 | **✗ 对称，分不开** |
| 提议的 `span_by_task`：${\rm sat}(P)$ | 0.074074 | 0.074074 | **✗ 合并，也分不开** |

**两个公式都分不开，原因不同但结果相同**：
原始公式对 $C$ 与 $T$ **等权平均**（对称），提议公式把两者**合并成配对数**（丢掉了区别）。

> **所以修正不是「换公式」，是「别把三个量合成一个」。**

我们据此实现的 `span_decomposed()` 返回三元组与诊断，
而不是一个标量。**这是一个度量设计上的教训**：
当一个量承载了两种相反的含义时，把它合成一个数不会「更方便」，
只会让两种含义都无法被读出。

### 3.4 `H=0` 的两种解释

在任务多样性实验（专家 / 通用 × coding / writing）中，我们测到：

```
general-C   coding:  H=0.811  {expert-A: 3, general-D: 1}
            writing: H=0.000  {expert-B: 3}
```

按「$H=0$ 表示结构性锁定」的直觉读法，这里会得出错误结论——
`general-C` 在 writing 上只调 `expert-B`，**而那正是能力性选择**（`expert-B` 是 writing 专家）。

**所以 $H = H(\text{callee} \mid \text{caller}, \text{task}) = 0$ 有两种解释：**

| $H=0$ 的含义 | 判别依据 |
|---|---|
| **结构性锁定** | 候选集里**没有**别的选择 |
| **能力性锁定** | 候选集里**有**别的选择，但一个明显更好 |

**区分它们需要第二维：能力对齐度**（被选中的 callee 在该 task 上是否真的更强）。
**「偏好 + 对齐」才是能力性不可替代性；只有偏好可能只是乱挑。**

## 四、主贡献二：四件缺一不可

可靠性的建立需要四个条件，**每一个都是前一个的"下一层"**。

### 4.1 哈希链（链内自洽）

$$
H_t = \mathrm{Hash}(H_{t-1} \;\|\; \text{CoreProfile}_t \;\|\; \text{Timestamp})
$$

**分段必须无歧义**：直接用分隔符会与内容里出现的同一字符混淆，
所以每段先带长度前缀。

### 4.2 洞一：哈希链防伪造，但不防重算

自检里有一条是这样写的：

```
✓ 重算整条链后自身自洽（所以必须锚定链尾）
```

**「篡改历史必须重算整条链，而这在算力上是不可能的」——这句话防伪造，但不防重算。**
重算一条账本只是一次循环，**新链自己校验是通过的**。

**补上的是**：把**链尾哈希写进链外凭证**（VC 的 `credentialSubject.ledgerHead`）。
重算出的新链尾与已签凭证里的旧链尾对不上，**而改凭证需要私钥**。

### 4.3 洞二：只锚链尾也不够

`ledgerHead` 是**最后一条的 hash**。于是：

```
改第 1 条的内容，不重算          → 链尾【不变】
查询端点用这个没变的链尾签发凭据  → 调用方验签【通过】
```

**调用方看到 `verified=True`，而服务方的历史已经被改过。**

**根因不在链，在端点**：**签发前没有校验自己的账本。**
修法是签发前先 `verify()`，失败则**拒签并返回 409**——
**而不是签一份"看起来有效"的凭据**。

**为什么必须用 409 而不是 200 + 空**：调用方要能区分
「**peer 不在**」与「**peer 在，但它的话不可信**」。
**把两者混为一谈，会让一个被篡改的 peer 与一个下线的 peer 得到同样的处理。**

**这个洞催生了第四个 MCP tool `circe.ledger_verify`。**

### 4.4 洞三：自动增量断了

用两个真实本地模型跑完之后：

```
③ 用真实日志独立算：density = 0.547333   ← 有值
④ 查询端点返回：    density = 0.0        ← 白纸，而账本已有 6 条
```

**「自动增量」名义上实现了，实际断了**：`current_profile()` 返回的是注入的固定值，
而 `update()` 写进账本的记录**没有回到剖面计算里**。

**为什么 76 项自指测试一条都没抓到**：`tests/` 里的 provider 与账本**从不同时使用**——
provider 是静态的，账本是分开测的。**只有当真实调用真的走完整条链
（模型回答 → Trust Update → 再查询）时，两者才第一次相遇。**

**修法**：`current_profile()` 改为**从账本重算**。
配套要改三处——**账本条目必须写下重算所需的全部字段**（`callee`、`stack_depth`）。

### 4.5 汇总：四件缺一不可

| 洞 | 在一个层次上做对了什么 | 但这个正确性依赖于 |
|---|---|---|
| 一 | 哈希链保证链内自洽 | **链尾的真实**（链尾可被重算） |
| 二 | 签名保证凭据不可伪造 | **端点的诚实**（端点签了个没变的尾） |
| 三 | 解释串让值可手算核对 | **输出的精度**（差了最后几位） |
| 四 | 账本记录了每次调用 | **剖面从账本重算**（写了却没读回来） |

**同一条形状**：

> **在一个层次上做了正确的事，但这个正确性依赖于另一个层次上没有被保证的东西。**

**四次的修法也同一条：把那个未被保证的东西补上。**

**而它们指向同一件事**：**每一层都在试图消除前一层的不确定性，然后引入自己的。**
修到洞三时已经没有下一层可推——**它就是最后一位**。

### 5.3 为什么"自检"与"stdin 往返"必须分开

`server.py --selftest` 是**进程内**的，证明「分发逻辑对」；**但它没有经过管道。**
而管道里有一批只在真实往返中暴露的问题：

```
· stdout 混入非协议输出（print 调试、库的 banner）→ 客户端解析失败
· 没有 flush                                    → 客户端永远等不到响应
· 行缓冲 / 编码问题                              → 中文乱码
· 子进程启动失败但父进程不知道
```

**这与 §4.5 那条形状同形**：**分发逻辑对 ≠ 管道能通。**

## 六、主贡献三：三个"看起来有效、实测无效"的检查

**我们认为这一类内容对本领域最有价值，也最少被报告。**

### 6.1 同名不同层：一个被制度化的事故

**事故**：我们把另一条线上「核剖面需要 LLM 判断」这一定义平移到 CIRCE，
从而造出一个「核剖面不确定 → `core_hash` 不稳定 → 哈希链会断」的问题，
并**为它认真地设计了三套方案、写了三条代价、请人裁决。**

**它为什么是假门**：

```
另一条线的核剖面：对一份【文本 / 概念图】做删除测试   → 需要 LLM
CIRCE 的核剖面  ：对一个【agent 的调用历史】做统计   → 不需要 LLM
                        名字相同，对象不同
```

**制度化**：事后仅把教训写进文档是**被动规则**——只有已经犯了错才会想起来。
所以我们把它变成**结构化数据 + 可执行检查**（`glossary.py` + `check_conventions.py`）：

```
① 术语借用声明   引入同名术语的文件必须声明与另一条线的差异
                 glossary 里两侧 needs_llm 必须「有记录且不同」
② 禁用短语       只在另一条线语境里成立的说法不得出现在 CIRCE 里
                 （**区分"主张"与"引述"**——记录这个错误的文字本身不算违规）
```

**第二次检查覆盖 140 条短语。** 而它的规则经过三轮精确化：
**第一版报了 13 处假警报**——而「报警变噪声、噪声变忽略」比没有检查更糟。
**所以改的是规则精度，不是把检查关掉。**

### 6.2 一个筛模型的工具：它筛不出它想筛的东西

**背景**：第一次生态实验发现某个模型从未产出合法 JSON，于是加了 `--check-models`，
用简单 prompt（「只输出一个 JSON 对象」）先筛一遍。

```
筛模型（简单 prompt）:      然后进入真实决策:
  qwen3-vl:8b      可用       agent-A: 不行动（没能解析出 JSON（370 字符））
  qwen2.5:7b       可用       agent-C: 不行动（没能解析出 JSON（389 字符））
  deepseek-r1:14b  可用
```

**两个通过筛选的模型，在真实决策里失败了。**

**原因**：筛选 prompt 与真实决策 prompt **复杂度差一个量级**——
前者只有一个短句，后者含人格、目标、工具表、核剖面块、历史。

**修法**：筛选必须用**与真实任务同构的 prompt**。

```
筛模型（同构 prompt）:
  qwen3-vl:8b      不稳定（0/2）   ✓ 正确识别
  qwen2.5:7b       可用
  deepseek-r1:14b  不稳定（0/2）   ✓ 正确识别
```

**同一个工具，换成同构 prompt 后立刻筛对了。**
上一轮我们写「它筛不出它想筛的东西」——**那句话对，但结论不是"筛模型没用"，
而是"筛选必须测同一件事"。**

### 6.3 一个未解的观察，以及它暴露的方法论问题

**现象**：用 tool calling 决策时，24 次里 18 次返回**空响应**（`content=''` 且 `tool_calls=[]`）。

**三个诊断，三个否证**：

| 假设 | 怎么测 | 结果 |
|---|---|---|
| `num_predict=200` 太小 | 200 / 1024 / 不设 | **全部成功** ✗ |
| prompt 太长 | 打印实际 prompt | **只有 233 字符** ✗ |
| 快速连续请求 | 串行+间隔 / 串行无间隔 / 并发 4 路 | **全部 0/4 空响应** ✗ |

**而诊断过程暴露了一个方法论问题**：

> **前两个诊断脚本用的是我们手写复制的 prompt。**
> 于是它们一直在测一个「与真实运行近似但不相同」的东西——
> **而"真实 prompt"这个说法本身从未被核对。**

第三个诊断改成 `import` 任务里真正的函数，才看到它只有 233 字符。

**这与本文那条主线索同形**：

> **一个层次的结论依赖于另一个层次上一个未经核对的假设。**
> 当时的假设是「我复制的 prompt 就是真的那个」。

### 6.4 三个检查的共同形状

| 检查 | 它做对了 | 但它依赖于 |
|---|---|---|
| 术语检查（第一版） | 能抓同名不同层的用法 | **引述与主张的区分**（否则 13 处假警报） |
| 筛模型（第一版） | 能测"模型会不会输出 JSON" | **筛选 prompt 与真实任务同构** |
| 诊断（前两个） | 能复现一个 prompt 的行为 | **那个 prompt 就是真的那个** |

**三者都犯了同一类错**：**验证的对象与被验证的对象不是同一个，而这一点没有被核对。**

**我们建议把这条写成一条可执行规则**：
**任何验证脚本都必须声明「它测的东西与真实运行的东西在哪一点上是同一个」。**

## 七、负面结果

**我们报告四个，因为它们限定了结论的适用范围。**

### 7.1 `span` 在固定配对的生态里结构上无法分化

第一个生态实验（5 个 agent，自主决策，9 次真实调用）测到：

```
agent-A → agent-B   （3 次，全是同一个目标）
agent-D → agent-A   （3 次，全是同一个目标）
每个被调用者因此仍然只有一个 caller
```

**问题不是「span 会不会分化」，而是「自主决策会不会产生多个 caller 指向同一个 callee」。**
**在固定配对的生态里，跑多久都不会。**

**任务多样性实验**（专家 / 通用 × coding / writing）打破了它：

```
expert-A   coding: 5 次   writing: 1 次   强项=coding   ✓ 方向对
expert-B   coding: 1 次   writing: 7 次   强项=writing  ✓ 方向对
general-C  coding: 4 次   writing: 4 次   强项=—        ✓ 均衡
```

**专家在它的强项上被调用得明显更多。** 这是"能力被识别"的直接证据。

### 7.2 「无引导对照」在本地模型上做不出来

**要回答的问题**：给 agent 看剖面但不给任何倾向性提示，它会不会**自发**支持
一个剖面为空的新加入者？（对照：给了提示时会。）

**实测**：

```
4 个 agent × 4 次决策 = 16 次
call=4, no_action=12      ← 12 次「没能解析出 JSON」
```

**同一个 `qwen2.5:7b`，在较简单的决策 prompt 下能稳定产出 JSON，
在含剖面块的 prompt 下不能。**

**换成 tool calling 也没有解决**（25% 成功率，18 次空响应，见 §6.3）。

> **要区分「剖面进入决策输入」与「剖面改变了偏好」，
> 前提是模型能稳定产出决策——而它做不到。**
> **这是能力的下限，不是实验设计的缺陷。**

**我们把它记为未解观察，而不是解决它**——因为：

> **CIRCE 的设计哲学是「判断留在链外」。**
> 链上只记录事实。**LLM 在调用方的决策过程是黑箱，这是有意的，不是缺陷。**
> 所以拿不到这个对照，CIRCE 仍然成立；那属于 **AI 行为科学**，不属于 CIRCE 的内核。

### 7.3 白纸问题没有自然解决

```
新加入者（账本为空）在单阶段实验里被调用 0 次
```

**没有任何 agent 去调用一个剖面为空的新加入者。** 这是**冷启动问题的直接呈现**。
CIRCE 的设计承认它（查询在账本为空时返回 warning 而不是假数据），但不解决它。

**两阶段实验里它被调用 2 次**——但那是**被提示的结果**（prompt 里写了
「也可以选择支持还没被调用过的」），**不是自发行为**。两者的区别很重要：

- 前者证明「剖面进入了决策输入并被使用」
- 后者才证明「agent 会自发补偿冷启动」

**本实验只证明了前者。**

### 7.4 时间衰减的真实尺度：本实验给不出

运行时长在秒级，半衰期（默认 30 天）内的衰减 ≈ 1.0。
**要测真实尺度需要跑几小时到几天。** 但我们已把要观测的量
（每次调用的时间戳）写进账本——**延长运行时间不需要改代码。**

## 八、相关工作

**元数据取自 arXiv 官方 API**（`tools/fetch_related_work.py`，结果落盘
`tools/related_work_meta.json`），不依赖作者记忆。

### 8.1 agent 声誉与信任

多智能体系统中的信任建立已被系统综述
（[*A Comparative Survey of Trust-Building Methods in Multi-Agent AI Systems*](https://ieeexplore.ieee.org/document/11417056)）。
近年针对 LLM 多智能体的工作包括
MiniRep（基于声誉的辩论聚合，arXiv:2609.39297）、
DART（区块链治理下的 DAG 声誉与激励，arXiv:2609.05529）、
DRF（动态声誉过滤，arXiv:2509.05764）。

**与 CIRCE 的差别在问法上，不在机制上**：这些系统输出的是**可信度**——
一个关于目标的、可以被聚合的成分；
CIRCE 输出的是**不可替代性**——一个关于**关系**的量，因此它的查询接口必须带 `caller`。
**一个高声誉的 agent 可能完全可替代**（别人也能做同样的事），
**而一个低声誉的 agent 可能是某个 caller 的唯一选择。** 后者正是 §3 要测的东西。

### 8.2 互操作协议

agent 协议已有一份覆盖 MCP / ACP / A2A / ANP 的综述（arXiv:2505.02279），
IETF 亦在推进用例与需求文档（[draft-rosenberg-agentproto-usecases](https://datatracker.ietf.org/doc/html/draft-rosenberg-agentproto-usecases)）。

**CIRCE 不在这一层竞争**——它是一个**服务**，不是协议（§2.4）。
**这是设计选择而非能力限制**：新造一个信任协议意味着要求对方先学会它，
而挂在 MCP 上意味着对方已经会了。

### 8.3 可验证凭证与 agent 身份

W3C 已成立 **Agent Identity Registry Protocol** 社区组
（[公告](https://lists.w3.org/Archives/Public/public-new-work/2026Apr/0007.html)），
学界亦有结合零知识证明的去中心化身份协议（DIAP，arXiv:2511.11619）。

**CIRCE 的实现直接使用 Ed25519 + W3C VC 数据模型**，不重新发明签名与凭证格式。
**我们贡献的是它们承载什么**：凭证里锚定的是**账本链尾**，
而 §4.2–4.3 说明**这个锚定位置的选择本身就是安全性的一部分**——
只锚链尾、不在签发前自校验，会签出一份「隔着被篡改的历史仍验签通过」的凭据。

### 8.4 测量效度 —— 本文 §6 的理论锚点

**这一节与本文关系最直接。**

Kearns（[*Quantifying construct validity in large language model evaluations*](https://arxiv.org/abs/2602.15532)，
arXiv:2602.15532）明确提出：LLM 评测中的核心问题是**构念效度**（construct validity）——
一个基准测的**是不是它声称在测的东西**。
Alaa 等（[*Medical LLM Benchmarks Should Prioritize Construct Validity*](https://arxiv.org/abs/2503.10694)，
arXiv:2503.10694）在医疗基准上给出了同方向的论证。

**本文 §6 的三个失效，本质上都是构念效度问题**：

| §6 的检查 | 它声称在测 | 它实际在测 |
|---|---|---|
| 术语检查（第一版） | 术语借用事故 | 术语**出现**（含引述），13 处假警报 |
| 筛模型（第一版） | 模型能否完成**本任务** | 模型能否输出 JSON（**一个更简单的任务**） |
| 诊断（前两个） | 真实运行的行为 | **我复制的 prompt** 的行为 |

**我们把它写成一条可执行规则**：

> **任何验证脚本都必须声明「它测的东西与真实运行的东西在哪一点上是同一个」。**

**这与效度理论的区别在于层次**：效度理论讨论的是**基准与能力**的关系，
而本文讨论的是**检查与待检事实**的关系——**包括本文自己使用的检查**。
我们把这一点视为本文对该方向的一点补充：**检查自身也需要被检查，而它失效的方式
与它要防的失效方式是同一种。**

### 8.5 抗女巫与「多个不等于多份」

Bara（[*Epistemic Sybil Resistance: Multiplying AI Agents Without Multiplying Evidence*](https://arxiv.org/abs/2609.01873)，
arXiv:2609.01873）指出：**增加 agent 数量不等于增加证据量**。
Shi 与 Joo（[*Sybil-Resistant Service Discovery for Agent Economies*](https://arxiv.org/abs/2510.27554)，
arXiv:2510.27554）从服务发现角度处理同一问题。

**这与本文 §3 同源**：如果 $k$ 个 agent 都只是同一个底层能力的复制品，
那么「被 $k$ 个不同 caller 调用过」与「被 1 个 caller 调用 $k$ 次」在
**不可替代性**上没有区别。
**CIRCE 的 `span_decomposed` 三元组可以看作这个观察在度量层的一个具体后果**：
只有把 $C$、$T$、$P$ 分开看，才能问出「这些 caller 是不是**独立地**需要我」。

## 九、局限与边界

1. **核剖面测的是「被调用分布」，不是「不可替代性」。**
   §3 给了区分的工具（`span_decomposed`），但**默认的 `span` 仍只测前者**。

2. **没有 ground truth。** 在生态里，「真实的不可替代性」没有定义。
   所以我们**不试图验证剖面是否*正确***，只观察它是否稳定、是否分化、是否随时间演化。
   **稳定性本身就是信号。**

3. **判断在链外。** 这不是缺陷，但它意味着**链上的事实不能推出"应该调用谁"**——
   那需要调用方自己的模型。

4. **实验规模小。** 最多 5 个 agent、每种配置几轮。**这足以暴露结构性问题
   （固定配对、白纸问题），不足以给出统计结论。**

5. **本地模型的能力下限限制了可做的对照。** 见 §7.2。

6. **一个被绕开的问题。** CIRCE 用调用历史替代了内容层面的测量。
   这是一个正确的转向（调用历史确定，内容判断不确定），
   **但它绕开而没有解决那个问题。** 我们把它记下来，而不是声称它消失了。

## 十、结论

CIRCE 的核心是一个**换掉的问法**（「删掉你，我会失去什么」）与一个**有意的分工**
（判断留在链外，链上只记事实）。

而这一轮工作最有价值的部分，**不是系统建成了，是它被实测推翻了四次**：

- **`span` 测的不是不可替代性**，而区分两种不可替代性**不能被任何两两合成的公式表达**
- **只锚链尾防不住中间改写**——签发前必须自校验
- **自指测试抓不到"自动增量断了"**——只有真实调用走完整条链才会相遇
- **三个检查看起来有效、实测无效**，而它们都是「验证对象与被验证对象不是同一个」

> **一条贯穿全部的线索**：
> **一个层次的结论，依赖于另一个层次上一个未经核对的假设。**
> 哈希链依赖端点、端点依赖链尾、解释串依赖精度、账本依赖重算、
> 诊断依赖「我抄对了」、筛选依赖「测的是同一件事」。
>
> **修法每次都一样：把那个未经核对的东西显式核对一次。**
